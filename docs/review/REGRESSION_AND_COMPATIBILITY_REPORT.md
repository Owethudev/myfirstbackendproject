# Regression and Compatibility Report

## Scope

This report assesses the proposed security/state-machine changes against current behavior. No code or deployment change is authorized by this document. Current source paths match `origin/main`; the worktree remains on a branch 39 commits behind main.

## Change impact matrix

## Data and API compatibility constraints

- Existing `Post` and `EventPost` owner identity is a string `author`; no immutable owner ID was identified. Any ID-based ownership schema requires a separately approved, additive migration/backfill, representative-data test, backup, and rollback plan.
- Existing user/session/content records must not be bulk-modified as part of guard fixes. Missing expiry or old string authors need explicit compatibility behavior.
- Keep existing route paths, status/payload shapes, public feed access, pagination, admin moderation, guest browsing, and local logout cleanup unless a separate behavior change is approved.
- Account deletion is admin-authorized in the backend despite normal-user UI. Preserve the authorization until policy is clarified.
- Email verification has no expiry field/check. Adding one needs a rule for already-pending accounts. Registration currently deletes the account if delivery fails; reset delivery failure leaves a token saved. Changing either partial-failure behavior requires a retention/retry decision.
- Netlify configuration exists. No Render manifest or live deployment verification is available. `VITE_API_BASE_URL`, `MONGODB_URI`, CORS settings, and provider secrets must be checked in the appropriate non-production environment, without copying values into reports.

## Rollback protocol

1. Use one reviewed feature branch and small isolated commits; preserve a clean baseline commit.
2. Use additive/code-only changes first. No data migration or bulk update without approval, backup, representative test, and reverse plan.
3. Keep previous API contracts where possible and test old-client behavior.
4. If a change fails tests or a staged check, revert only its feature commit; do not reset or overwrite unrelated work.
5. Do not deploy as part of implementation. Production rollback requires an explicitly approved deployment plan.
